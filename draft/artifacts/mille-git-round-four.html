mille-git Round Four

Spec review · round four

mille-git: two blockers, and a product mismatch

The engineering in this draft is unusually good — the merge rule, the header-before-load diff refusal, the takePendingChanges prohibition and the TSFN-only EventBus catch are all real, hard-won findings. Two of its normative rules, though, are provably wrong against real git, and the product it is an engine for does not exist in the design source.

Blocking — normative rules that cannot be satisfied

Both were reproduced against git 2.50.1 in a scratch repo. Each contradicts a rule the spec marks MUST, and one of them is the mitigation for the spec's own highest-rated risk.

B1 §10.6 · §11.2.1 · T-MERGE-RENAME · §26 “Path-limited replace wipes dirty list”

The rename merge rule can never fire, so the phantom row it exists to prevent survives

Spec says
“Always drop any prev row whose path equals any run row's origPath… whether H is {b.ts} or {a.ts,b.ts}.”
Real git
A pathspec-limited status that sees only one side of a rename reports D or A — never R, and never an origPath at all.

Rename detection is a pairing over the whole change set. Constrain the pathspec to one side and there is nothing left to pair with, so git degrades to the unpaired letter: 

$ git mv a.ts b.ts

$ git status --porcelain=v2            # full
2 R. N... R100 b.ts\ta.ts          ← origPath present

$ git status --porcelain=v2 -- b.ts     # hint = {b.ts}
1 A. N... b.ts                          ← no origPath. ever.

$ git status --porcelain=v2 -- a.ts     # hint = {a.ts}
1 D. N... a.ts

Walk T-MERGE-RENAME with that: prev holds a.ts; the run returns A b.ts with no origPath; the drop rule never triggers; a.ts is not in H so the keep rule preserves it. The published snapshot lists both a.ts and b.ts — a file that no longer exists, sitting in the Changes list until something forces a full status.

This is reachable on the ordinary path, not a corner. §11.2.1 routes renames by recovering from via pathForId(old_parent_id) + old_name, and then says that when old_parent_id is missing — lazy or unwalked folders, which is most of a large tree — “hint only to and rely on §10.6 dropping origPath when gix reports the rename.” That is precisely the case proven above to report no rename.

Suggested fix A rename hint must never be path-limited. Either route both sides and escalate to a full status whenever from is unrecoverable, or — simpler and cheaper than it sounds — treat every kind: 'renamed' event as a full-status trigger. Renames are rare next to writes, and this buys back the merge rule's correctness outright. Then rewrite T-MERGE-RENAME to assert the escalation, because as written it asserts behaviour git does not have.
B2 §15.3 · §15.4 step 4 · §9.2 step 6 · AC-006

The commit flow breaks on a repository with no commits yet

Spec says
unstage is “git restore --staged -- then git reset HEAD --”; commit step 4 unstages the excluded set with git restore --staged.
Real git
On an unborn HEAD, git restore --staged exits 128 with fatal: could not resolve HEAD. Plain git reset -- <paths> succeeds. 
$ git init && git add a.txt b.txt   # no commits yet

$ git restore --staged b.txt
fatal: could not resolve HEAD          rc=128

$ git reset -q -- b.txt
rc=0                                   → A a.txt / ?? b.txt

$ git rev-parse --abbrev-ref HEAD
fatal: ambiguous argument 'HEAD'       rc=128, prints "HEAD"

The failure lands exactly where an ADE lives: an agent scaffolds a project, the room offers an include-set that is a subset of what is staged, and the first commit — the very first commit of the repository — fails at step 4. §15.3's fallback ordering makes it worse: restore --staged runs first and aborts before reset HEAD is reached, and reset HEAD would fail on unborn too. The working form is reset with no revision.

§9.2 step 6's CLI identity fallback has the same hole: rev-parse --abbrev-ref HEAD exits 128 and prints the literal string HEAD to stdout, so a naive read yields branch "HEAD" and detached: true for a fresh main. Use git symbolic-ref --short HEAD, which is correct on unborn.

None of the 18 acceptance criteria and none of the ~40 test IDs exercise a repository without commits.

Suggested fix Detect unborn HEAD once at open() (git rev-parse --verify HEAD fails, or gix reports an unborn ref) and carry it on the session. Branch the unstage path on it: reset -- <paths> when unborn, restore --staged otherwise. Read the branch with symbolic-ref --short. Add T-UNBORN to §28.2 covering identity, first commit of a subset, and unstage.

High — the engine and the product are aimed at different targets

The spec is disciplined about what it is not building. The problem is that what it does build has no consumer in the design source, and the consumer that does exist needs something the engine cannot express.

H1 agent-history-proto §03 col ⑤ · design-agent-history.md §8, Q4

The design source contains no GitHub Desktop replacement — it explicitly refuses one

The proto's git column is read-only. There is no click handler on #ah-foot at all; the only wired control is the Changes / History segmented switch. No diff view, no staging or discard buttons, no include checkboxes, no commit box. The refusal is stated verbatim, twice — in index.html:806 and again in the design doc: 

"Not pressable — this proposal has no diff view,
 and a hover fill would be promising one."

And the whole column is an open question, not settled design: “Q4 — the footprint rail, keep or kill. §8. The one idea here most worth arguing about.” The doc's own build order excludes it: “Not the footprint rail until Q4 is answered — it is the only item here that asks the index for something new.”

So the spec's §32.5 deferral — “where the Changes/History room lives … MUST NOT block mille-git” — understates it. It is not that the room's location is open; it is that the room as designed needs roughly a fifth of this engine, and the room you actually want (repo-scoped, with diffs and commits, replacing GitHub Desktop) has never been designed. Nine PRs of engine would land against a UI brief that does not exist.

Suggested fix Settle Q4 and draw the repo-scoped Changes/History/Diff room before PR 5. The engine's diff protocol in particular is unfalsifiable without it: §13's hunk shape, the 256 KiB auto-render cap and the tooLarge contract are all guesses until a design says whether the view is unified or split, virtualized, and syntax-highlighted.
H2 §17.1 GitService · proto col ⑤ footprint contract

The panel the design does specify is session-scoped, and nothing can answer it

GitService offers
status(worktreePath) — everything dirty in the repository, right now.
The design asks
“what this session changed, and what it committed” — files attributed to one agent session, partitioned into committed / staged / unstaged.

The proto is explicit that the scoping is the idea: “Both are scoped to the session rather than to the repository — that scoping IS the proposition.” Answering it needs a join between a session's touched-file set and git's status — and that join exists nowhere. Rosetta's daemon has the session data and no git surface at all (no git route in crates/server/src/http.rs, no git type in protocol); mille would have the git data and no notion of a session.

Worth deciding deliberately rather than discovering in PR 8: either the room becomes repo-scoped (which is what a GitHub Desktop replacement means anyway, and drops the requirement), or something must own that join — most naturally rosettad, which already ingests per-session file-touch events.

H3 §10.2 · §4.2 · §21.6 · proto subtree()

This is a git status engine, not the git tree backend the goal calls for

Engine emits
entries: readonly StatusEntry[] — a flat array of repo-relative paths, up to 10,000.
The view draws
two mille trees — “Staged” and “Unstaged” — each a real subtree with indent guides, chevrons, and directories kept when any descendant survives.

Between those two sits work nobody has assigned: reconstruct the parent chain from flat paths, prune to a subtree per group, drop the root and decrement every depth, reconcile against EntryStore ids so rows can share the shipped component's selection and decoration state, then window it for virtualization. The spec pushes all of it to JavaScript — §4.2 makes “replacing the FileTree with a Changes list” a non-goal and §21.6 assigns virtualization to “ADE UI, not this spec.”

That is the one place the stated goal — a state-of-the-art git file tree backend, in Rust, because multi-agent churn is relentless — is not met. Under sustained churn the renderer re-shapes up to 10,000 flat paths into a tree on every publish, per worktree, in the one process that must not stutter. And mille already has the tree: EntryStore holds parents, children, ids and depths, and the walker keeps them current.

Suggested fix Add a tree projection to the engine: emit status pre-shaped as grouped subtrees with parent ids and depths, joined to EntryStore ids where they exist, and diff it generationally so the renderer applies a delta rather than rebuilding. This is the piece that makes it a git tree backend rather than a porcelain parser with a watcher, and it is where the Rust actually earns its place.
H4 §21.5 · §6.2 · AC-008

No bench covers the workload the engine exists for

All three planned benches are quiet-repo benches: warm path-limited 50 files, cold full status on a generated 5k-file repo, and a diff fixture. The reason this engine is being built — eight worktrees under continuous multi-agent write pressure — has no bench, no budget line, and no regression gate.

§6.2's closest row, “Agent writes 40 files in 1 s → one coalesced status,” describes a burst. Steady state is the hard case: at a 75 ms debounce, sustained churn yields on the order of 13 status runs per second per worktree, and eight worktrees put ~100 gix status runs per second into the same process as the explorer's walker and watcher — which are saturated by the same file events, by construction. AC-008 only asserts that two statuses can overlap in time; it measures nothing under load.

Suggested fix Add the campaign bench the workload deserves, and make it the merge gate: N worktrees × a synthetic agent writing at a fixed rate, reporting p50/p95/p99 for status latency and for explorer delta latency, so contention between the two subsystems is visible. Rosetta's own convention already demands this shape — frozen before/after pairs from one checksummed snapshot, with campaign ID and machine recorded.
H5 §21.2 · §21.1 · advisePerformanceConfig

The two recommended accelerators do not accelerate the primary read path

Spec says
Set core.untrackedCache and core.fsmonitor on ADE-created worktrees — “it makes gix/CLI status cheap.”
gitoxide
lists fsmonitor and untracked-cache among planned big-repo accelerators, not shipped ones.

Since gix is the primary read path and the CLI is the fallback that §21.1 explicitly exempts from the 80 ms warm budget, the advice only speeds up the path that has no budget. Worse, there is prior art pointing the other way: starship's gix migration falls back to the git CLI whenever core.fsmonitor is set. Following §21.2 on ADE-created worktrees could push you off gix on exactly the repositories the ADE controls.

Keep advisePerformanceConfig — it is right for the CLI fallback and for whatever the user runs in a terminal — but stop describing it as a gix optimization, and re-verify against the gix release you pin before relying on it.

H6 §21 (absent)

Nothing reuses the parsed index between status runs

Every status run — path-limited included — re-reads and re-parses the index. In a 100k-file repository that is a multi-megabyte parse, and under the steady state in H4 it happens ~100 times a second across eight sessions. It is the single largest available win for this workload and the spec does not mention it.

The invalidation signal is already being built: the gitdir watch in §11.3 fires on index. Confirmed empirically that a commit rewrites the index file (mtime and size both change), so the watch is a sound cache key.

Suggested fix Hold a warm parsed index per session, invalidated by the gitdir index watch plus an mtime/size check. Land it in PR 3 alongside the watch that invalidates it, and bench cold vs. warm as part of H4's campaign.

Medium — wrong premises and undercounted blast radius

M1 §20.4 · §15.1 · T-ALIAS · T-ALIAS-ADD

The alias hardening blocks an attack git already blocks, and misses the two that work

§20.4 makes an eleven-pair -c alias.<verb>=<verb> prefix normative on every spawn, and adds a standing rule that new verbs must ship their alias override in the same PR. Git does not need it — an alias that shadows a builtin is ignored: 

$ git config alias.status '!touch PWNED'
$ git status --porcelain
ls: PWNED: No such file or directory    ← alias never ran

$ git config core.fsmonitor "$PWD/fsmon.sh"
$ git status --porcelain
FSMON_RAN                             ← executed, on a read

$ git config diff.external "$PWD/extdiff.sh"
$ git diff
EXTDIFF_RAN                           ← executed
$ git diff --no-ext-diff
ls: EXTDIFF_RAN: No such file or directory

T-ALIAS and T-ALIAS-ADD therefore pass with the mitigation deleted — they do not test what they claim to test. Meanwhile the two keys that do execute are unmentioned, and §15.1's argv sets no --no-ext-diff. This matters more here than in a normal editor: an ADE opens worktrees that agents created and repositories that were just cloned, so repo-local config is attacker-adjacent by default.

Suggested fix Drop the alias prefix (keep one test documenting why it is unnecessary). Add --no-ext-diff to every diff spawn, and neutralize the keys that actually run commands: core.fsmonitor, diff.external, core.pager, core.hooksPath, credential.helper, and the *.textconv / *.process filter family. Rewrite T-ALIAS as T-CONFIG-EXEC against those.
M2 §11.5 · §3.1 watcher row · §11.2.1

“.git is ignored by the walker” is not true, which changes the watcher plan

Spec says
“Explorer respectIgnore: true skips .git content. That is why gitdir watch is mandatory even with path hints.”
mille-core
include_hidden: true and empty exclude_globs — the walker descends into .git. Only snapshot.rs:49-51's is_os_or_vcs_noise hides it, at projection time.

Two consequences. First, .git entries are walked, ID-allocated and resident in EntryStore — in a repository with many loose objects that is real memory and real walk time, and it is a mille-core question worth raising separately. Second, and more useful here: if the walker descends into .git then the watcher covers it too, so the explorer's 'event' channel is probably already delivering HEAD and index writes — which §11.2.1 then filters out, just before the spec adds a second notify watcher to observe the same files.

Suggested fix Measure before building: log 'event' paths during a git add and a commit. If gitdir events arrive, the second watcher becomes a fallback for the unbound case rather than a mandatory component, and §11.5's rationale needs rewriting either way.
M3 §11.1 · §11.3 · §11.4

In a linked worktree, branch refs live where nothing is watching

§11.1 assigns “gitdir HEAD, index, refs/, packed-refs” to the gitdir watch, and §11.4 watches <common>/worktrees/. For a primary checkout gitdir equals commonDir and refs are covered. For a linked worktree they are different directories — and branch refs are not in the per-worktree one: 

$ ls .git/worktrees/r3-wt2/
commondir  gitdir  HEAD  index  logs  ORIG_HEAD  refs

$ ls .git/worktrees/r3-wt2/refs/
(empty)

$ ls .git/refs/heads/
main  wt2branch                       ← both live in commonDir

So <common>/refs/ and <common>/packed-refs are watched by nobody. Local commits still refresh, because they rewrite the per-worktree index — but a fetch, a ref update from a sibling worktree, or any branch move made outside this session goes unseen until something else forces a status. Given that the spec rates linked-worktree watch silence a High risk already burned once, it is worth closing.

M4 §3.5 · §10.3 · rosetta WorktreeHeader.tsx

The Rosetta projection silently changes the number the header shows

§3.5 presents the GitFacts projection as a faithful drop-in. It is not: Rosetta counts lines from plain git status --porcelain, which collapses untracked directories, while §10.3 mandates UntrackedFiles::Files to match -uall. Same tree, different number: 

$ git status --porcelain          # rosetta today
?? loose.txt
?? newdir/                          count: 2

$ git status --porcelain -uall    # engine
?? loose.txt
?? newdir/a
?? newdir/sub/b                     count: 3

Any repository with an untracked directory changes what branch · n dirty reads after the swap. The engine's number is the more honest one — and the proto argues for exactly that, insisting the dirty count be “not the number of letters this tree happens to be drawing.” It just needs saying in §3.5 rather than being discovered as a regression.

M5 §19.5 · PR 8 · rosetta clients/app/electron/fx-host.mjs

Rosetta is not a downstream consumer to notify later — it already runs the migrated topology

§19.5 puts Rosetta “out of mille's PRs.” But Rosetta already runs the exact arrangement PR 8 exists to migrate: a UtilityProcess host importing createFileExplorerHost, registerGitDecorations and createShellGitClient, wired over MessageChannelMain — with both mille packages symlinked from this working copy via file: dependencies, so it consumes the crate at head rather than a published version.

Two consumers, then, not one: the playground and Rosetta, plus Rosetta's separate execFile git in electron/main.mjs. Sequence PR 8 knowing that, and the shell-client deprecation window in §24 has to cover both.

What holds up

  • gix 0.87.1 is real and correctly characterized. Published 2026-08-25; every named feature exists; Repository is Send only with parallel and is not Sync, so §9.2's ThreadSafeRepository + to_thread_local() requirement is right, and it is the kind of thing that costs a week when missed.
  • UntrackedFiles and the collapse concern are real. The enum has None / Collapsed / Files exactly as §10.3 assumes, and the nested-untracked failure it guards against is a genuine trap.
  • The EventBus finding is correct and non-obvious. events.rs really does hold only ThreadsafeFunction slots, so bindExplorer genuinely cannot be built without adding native subscribers. The snapshot-and-drop emit pattern is there for a documented re-entrancy deadlock, and §11.2's insistence that the callback may only arm a timer under policy_gate is the right read of a real hazard.
  • The takePendingChanges prohibition is exactly right — the host coalescer drains it once per tick, and a second drainer would silently empty explorer deltas. Rating it High and giving it a regression test is good judgment.
  • Header-before-load in §13.2 is the correct shape for diff refusal, and T-HEADER-SIZE tests it the right way, by injecting a failing reader rather than trusting a large fixture.
  • Every checked claim about the current codebase held except the three noted above — 41 verified across mille's Rust and TypeScript and Rosetta's app, including exact line numbers. The spec also correctly identifies two repo-doc bugs (the stale unknown-glyph comment, the false warn-once promise) and chooses the code over the comment.

Verdict

The engineering is sound; the sequencing is not. B1 and B2 are ordinary bugs in a draft — an afternoon each, and both belong in PR 2 and PR 4 respectively rather than being discovered in integration. The structural problem is that PRs 1 through 9 build a repo-scoped status, diff and log engine for a room that the design source explicitly declines to draw, while the room it does draw asks a session-scoped question no component can currently answer.

And on the stated goal — speed under multi-agent churn — the draft stops one layer short. It specifies a fast way to compute status and hands back a flat array, leaving tree-shaping, id reconciliation and windowing to JavaScript in the process that must not stutter, with no bench for the workload and no warm index. H3, H4 and H6 are where the Rust would actually earn its keep.

Order I would put on it:

  1. Fix B1 and B2 in the spec now — both change normative text and one invalidates a named test.
  2. Settle Q4 and draw the repo-scoped room, before PR 5 freezes a diff protocol against nothing.
  3. Decide H2 deliberately: repo-scoped room, or give rosettad the session↔file join.
  4. Add the tree projection (H3) to the crate's charter — it is the difference between a git tree backend and a porcelain parser with a watcher.
  5. Write the churn bench (H4) before PR 3, so the queue and debounce are tuned against the real workload rather than a quiet repo.
  6. Sweep M1's config-execution keys into §20 while the security section is still being edited.

None of this argues against building it in mille, in Rust, with gix for reads and the CLI for writes. That call looks right, and the draft defends it well.
