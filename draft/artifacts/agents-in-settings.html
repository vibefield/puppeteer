Agents in Settings

Installed agents, their versions and updates, what each one has loaded, and the accounts they sign in with — designed as two pages of the VibeField Settings sheet, under DESIGN.md, with a first-run that follows the Setup Assistant's laws.

The move

Godview watches. Settings manages.

The Godview drawer put installs, updates and accounts inside the control room. That was the right place to see them and the wrong place to change them: Godview is a stage, free in its looks, and it covers the window. Management is a document, and VibeField already has the document — the Settings sheet, where plugins get their source badge, their user-initiated updates and their two-step uninstall, and where the Account page keeps the user, the users on this machine, the link and the switcher.

So this pass moves the whole drawer into Settings and keeps only the marks in Godview. Two pages: Profiles, which sits under Account because it is about who you are signed in as, and Agents, which sits under Workspace beside Plugins because it is about what is installed. Every element below is one of the sheet's existing pieces, cited by section; nothing is styled fresh.

What stays true from pass 2. A profile holds one account per agent, and several profiles run at once. Nothing signs in by typing — every sign-in is the agent's own command, run in that profile's folder, and the row believes only what the agent reports back. Updates are the agent's own updater. This Mac is the first profile: the agents' own folders, adopted as they are.

What changes. The bar, the crate, the overlay and the initials are gone; the sheet's sidebar, header and sections replace them. A profile is a §2.6 tint, the same eight slots the user picks from, so the mark that reaches a card or a bubble is the one grammar VibeField already has for grouping. The first run is not a three-step sheet but two or three Setup Assistant panes, one decision each, every skip naming its later home.

The map

Two pages, and where a profile sits in the model

VibeField already has a persona: the user, minted on first run, with a name, an accent and one optional tailnet. Users are switched, never run side by side. That is exactly the wrong grain for subscriptions — the point of a second Claude Max is to use it at the same time as the first.

So an agent profile lives inside a user. One user, several profiles, each a named set with one account per agent, each with its own folder under the user's root, each usable at once. The machine's own agent folders appear as the first profile, This Mac, shared by every user on the machine because they are the same OS home.

The word collides once: the Account page already has a "Profile" block for the user's name and colour. The recommendation keeps the user's word for the agent thing, because it is the word James uses, and retitles that block "You".

Signing in, switching, and what really happens

A sign-in is the agent's own login command, started in this profile's folder. The row opens and the terminal appears beneath it — one element, in place, inside the sheet — with the agent's real prompt. When the agent reports an identity the terminal closes and the row wears it. Switching an account is the same pair in reverse: a two-step confirm, the agent's sign-out, then its sign-in, on the same folder, so plugins, skills and history stay.

Removing an agent stays with its installer. The row says which one.

Update results are three kinds of honest. A release feed answers with a number; the agent's own checker answers "current"; an app that updates itself, or an agent with no feed, says so instead of pretending. The orange dot marks only the rows with a newer release, which is the one thing here that asks for an act. The update itself is the agent's updater in a terminal beneath the row, and the version the row shows afterwards is the one it read back, never the updater's last line. Latest versions are example values.

Open items

  • Uninstalling an agent. Left with its installer on purpose. A "More" overflow could show the exact command; a one-click removal that runs npm or brew is a decision for a later pass.
  • Project-scope extensions. A project's .claude or .agents/skills belongs to the card that opened the project, not to this page. Only user scope lists here.
  • Windows and Linux paths. The rows print whatever the agent's own files say; the WIN track's path grammar applies unchanged.
  • Usage and quota per account. Pass 2 put it on the Godview usage column. Whether the Profiles row should also carry the plan's remaining quota is unresolved; it would be a §2.5-coloured number and belongs to monitoring.
  • The runtime. Everything on the Profiles page exists in puppeteer's phase 1 (profiles, roots, login invocations, verify). The Agents page's extensions block is designed ahead of track C, and the "Also install in…" verb needs each adapter's install command.
