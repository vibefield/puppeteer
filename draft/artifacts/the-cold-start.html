The Cold Start

First open, the archive is frozen. Today the daemon thaws it in private and hands over a finished room five minutes later. This design makes the thaw public: consent first, lists in seconds, and every project and session warming at its own pace — with a state grammar the whole room shares.

Where the machine already is

More of this exists than it looks. The pipeline was rebuilt into exactly the right three phases, and the readiness fact the UI needs is already on the wire:

discovery
discover() probes every adapter's data root and reports a census — installed, file count, total bytes, newest touch. It deliberately leaves enabled = false: "the app shows the result and the USER decides." Consent is designed in; nothing surfaces it yet.
meta ingest (skim)
meta_ingest reads bounded head/tail windows only — project and session lists exist before any transcript body is read. Seconds, not minutes.
stream ingest
Per-file transactions, newest-modified first. The commit granularity for per-session progressive reveal already exists.
readiness on the wire
SessionRow.stream_state — pending → streaming → indexed — is in the protocol and the generated TS bindings. The app just never reads it.
the blocker
rosettad serve binds its HTTP listener only after the whole backfill publishes; a fresh install cold-loads into a private temp projection, invisible until an atomic swap. /api/status itself 500s while the projection file doesn't exist. List endpoints serve from the hub's meta mirror, which warms only after publish. So on the one run that matters — the first — the app can't even connect.

The decision — the thaw goes public

Three ways to spend the first five minutes:

A · Atomic publish + a progress screen

Bind early, report phase and counters, reveal everything at the end. Honest, cheap — and it is a loading bar, not an experience. Ships first as the floor (slice 1), never the ceiling.

B · Meta-first, swap at the end

Lists in seconds, transcripts and figures all at once later. The section-level states work; the per-session "every second something new" does not.

C · Progressive publication — recommended

First-run backfill writes the public projection: skims land in seconds, then per-file stream commits flip sessions pending → indexed one by one, newest first, with FTS deferred to the async search worker (the search_dirty queue the conventions already reserve). Search readiness stays the separate, already-surfaced fact. rebuild keeps its private atomic path — it is a repair tool; correctness over liveness.

The honest cost of C: per-batch index maintenance and per-file commits lose to the bulk private load on total time. But the bulk path's five minutes buy nothing visible until minute five; C buys a usable room at second ten. Per the repo's own perf convention this is settled by a frozen before/after pair on ingest-bench, against acceptance gates rather than hope:

gates for slice 3 time-to-lists < 10 s · time-to-first-readable-session < 15 s · total wall time ≤ 1.5× the private path — measured on the frozen checksummed snapshot, logical counts equal. Misses the last gate → batch N files per transaction until it doesn't.

The wire contract · L3

Additive; protocol stays v1. DaemonStatus grows an ingest block fed from the pipeline's always-on atomic counters (the Instrument), so the transport reads live numbers even while the writer thread is deep inside a blocking backfill call:

IngestPhase        = discovering | backfilling | live
BackfillState      = queued | skimming | streaming | done

IngestProgress     { phase: IngestPhase, runtimes: RuntimeBackfill[] }
RuntimeBackfill    { kind:            string,
                     state:           BackfillState,
                     files_total:     number,   // census denominators, from discovery
                     bytes_total:     number,
                     files_skimmed:   number,   // skim meter:   files_skimmed / files_total
                     bytes_streamed:  number,   // stream meter: bytes_streamed / bytes_total
                     sessions_total:  number,   // known once skimmed; 0 before
                     records:         number }  // transcript records parsed so far
  • /api/status answers from process start, projection file or none (canonical_ready: false until then). It is the app's connectivity truth.
  • During backfill the hub mirror re-warms from the projection every ~2s and fans the diffs to /ws/meta subscribers — the app's existing meta feed sees sessions appear and stream_state flip with no new endpoint.
  • Slice 4 adds GET /api/discoveries (the census) and POST /api/runtimes/enable (consent, persisted in the runtimes table — serve stops force-enabling everything it finds). Phase grows awaiting_consent.
  • Slice 5 adds POST /api/ingest/boost {session_id}.

Onboarding · the roll call

One screen, not a wizard. Discovery is a read-only walk that finishes in about a second — the user never watches it; they arrive at its results:

  • A column of agent rows: mark, kind, data root in mono tilde form, and the census — 1,209 files · 2.1 GB · touched 3h ago. Checkbox, pre-checked for every installed agent.
  • Agents not found on this machine sit below the fold, quiet and unchecked — honest, and doubles as "here is what rosetta speaks."
  • One primary action — Begin ingest — and one reassurance line under it, because this screen is where trust is decided: "Everything stays on this machine. Nothing is uploaded." The literal truth of the localhost-only daemon, stated exactly once, here.
  • The button doesn't lead to a spinner; it leads to the room, veiled. Re-runnable from settings when a new agent appears.

The veil system · a readiness grammar

law 1 — readiness is data, never a timer Every scope derives pending | partial | ready from wire facts: stream_state, the ingest phase, and nothing else.
law 2 — only the ready may claim emptiness "No sessions" while ingest runs is a lie. A scope that isn't ready shows its veil; the empty state is reserved for a truth. The flash-of-empty-state bug dies by construction.
law 3 — a veil overlays, geometry holds (H-2) Cards render at final size from day one — placeholder digits in fixed tabular slots — so nothing reflows when figures land. And a veil never descends on a scope that has already been ready: a new agent's sessions join a live room as cooking cards, not as a re-frost.

Item scope — the cooking card

Meta facts are real from the first skim: title, agent chips, timestamps render as themselves. Only the quantitative slots are unknown, and those slots carry the state — never a spinner per card (forty spinners is noise, and a spinner says "blocked," which is false).

Section scope — the veil

One component wraps any section: a frost (backdrop blur ~5px over the panel tone at ~0.55 alpha) with the room's slim meter and a single label line — preparing · 2,314 of 5,912 sessions. The critical choice: content underneath keeps rendering and updating. Watching cards populate and figures climb behind frost is the progress animation; the meter is just the caption. Meters are determinate — the skim reports files, the stream reports bytes against the census.

Choreography · the first five minutes

  1. t+0sThe daemon binds instantly; the app connects on first paint. Fresh install → the roll call. Returning user → the room, already warm from the last projection.
  2. t+2sBegin. The room mounts veiled; project cards materialize behind the projects frost within a second or two. Skims land runtime by runtime — the shuffle-in is wanted motion, and it happens under frost where reordering can't disorient.
  3. t+10sAll skims done; the projects veil lifts — one dissolve, ~300ms. The crown (default selection) keeps its spend rule; newest-first ingest means the figures that decide it are the freshest ones, and the crown is sticky once placed.
  4. t+10s → doneFigures resolve newest-first, interleaved across runtimes. Your most recent project is typically fully lit inside the first minute; its summary panel unveils then. Anything you click is boosted to the front of the queue.
  5. the endThe portfolio panel unveils; phase flips live. The room is plain again; the veil system goes dormant until a new agent is enrolled.

Restarts skip nearly all of this: the projection already exists, the mirror warms from it before the listener even answers, and only changed sessions cook.

Boost · attention-directed ingestion

The queue is priority-ordered anyway — let the user's gaze reorder it. Click a pending session and the app posts boost; the daemon moves that file to the head; one transcript parses in well under a second, so the transcript veil lifts about as fast as a normal load. Same for a pending project (boost its newest N sessions). The subjective effect is disproportionate: nothing you actually reach for is ever not-ready, so the backfill stops being a wait at all — it's ambient warming of things you haven't looked at yet. One endpoint, one queue hop, one line on the transcript veil: in line — 214 ahead · reading now ↵.

Verified live: status answered with climbing byte meters while the projection file did not yet exist.

2

The veil system in the room · L3 / app — ✓ landed (913b734)

Readiness derivation from stream_state + phase; the veil, the cooking card; empty-vs-pending law enforced in every column and panel; adaptive polling while the phase isn't live; the fresh-install warming room. Photographed: warming at 86%, mid-backfill veils over growing charts, the settled room with no veil anywhere. Degrades cleanly against an old daemon.

3

Progressive first-run publication · L2 — ✓ landed (041e905)

First-run backfill writes the public projection per-file with FTS deferred to the async search worker (search_dirty lands with its consumer, per the repo rule); effects or mirror re-warm keep readers current; rebuild stays atomic. Ordering: interleave runtimes round-robin, newest-first within each — 5,912 claude-code sessions must not starve grok's 131. Judged by the three gates above on the frozen ingest-bench pair. Note for the implementer: serve's stream loop is already per-file (slice 5), so the unit of publication is already in place — this slice is "point it at the public projection and defer FTS."

As landed (schema v7): the FTS index moved out of the projection entirely — a disposable detached FTS5 sidecar built by an async worker that reads one canonical snapshot and acks the single writer; same columns and tokenizer, so BM25 and snippets are unchanged. All three gates passed on the frozen six-adapter pair: lists 5.82 s · first readable 13.86 s · total 1.349× (canonical alone 1.03×; search finishes warming after). Re-verified live on a fresh db: sessions flipped pending → indexed through the ordinary endpoints while canonical_ready was still false, canonical and search readiness surfacing independently — the veil UI lit up with zero app changes. Interrupted backfills now resume instead of discarding.

4

Consent — the roll call · L3 + app — ✓ landed (192ac9d, d54fe26)

GET /api/discoveries (census only, never content), POST /api/runtimes/enable (one-shot, installed kinds only, local-origin-guarded), phase awaiting_consent; serve no longer force-enables — the projection's enabled flags ARE the consent record, so enrollment happens exactly once and restarts skip the roll call. --agent/--all-agents are the headless stand-ins. The screen: census rows pre-checked, absent agents quiet below, one Begin act, the trust line stated exactly once.

5

Boost · L3 + app — ✓ landed (192ac9d, d54fe26)

The stream queue is driven one file per call; POST /api/ingest/boost drains between files and moves the opened session's file to the front. The audit lane is disabled per-file and runs once over the full roster at the end — checkpoints make that exactly the single rotating forced replay it always was. The app boosts automatically on selecting a pending session. Verified live: a boosted queue-tail session indexed while 32 newer sessions were still pending. Bonus: graceful ctrl-c now lands between files, not minutes away.
