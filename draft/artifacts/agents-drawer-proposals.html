Godview · proposalsthe Agents drawerpass 2 · 2026-09-06as builtdecisions

A profile is who you are across every agent, and a terminal opens into one.

Pass 2 turns the model around. The build treats an account as one agent's data root, listed under that agent; a person thinks in profiles: Personal, Work, each holding one signed-in account per agent. This pass makes the profile the first-class thing, adds the onboarding that sets one up, answers how signing in actually works, and keeps pass 1's installs and bar picks. Nothing new is coloured.

02

The review

What the build gets right: the drawer wears the instrument skin, every action is a runtime service, no row is tinted, and the second Grok copy is shown rather than hidden. The problems are about weight and words, and about where accounts stop.

  • Modelthe first-class thing
    Accounts are filed under agents; people live in profiles.The build lists Claude's accounts under Claude and Codex's under Codex, with a "default" per agent. Nobody thinks "which Codex account"; they think "am I at work or at home". A profile holds one signed-in account per agent, a terminal opens into a profile, and switching means either changing the account inside the profile or making another profile.
  • Rule 2state is a mark
    Two questions, one tab bar, no summary.The bar says AGENTS and nothing else. Whether six installs are behind or an account signed out is only known after opening the drawer and pressing ten CHECK buttons. The decided bar carries counts for blocked, working and idle; this state deserves the same treatment, in the tools group where it belongs.
  • Rule 2weight by role
    Every row is the heaviest row.A current install spends a five-fact grid and two buttons, exactly like one that is behind. The thing you scan for, current · behind · unchecked, is a boxed word that only appears after a manual check. It should be the row's one mark, and the facts a whisper beneath the line.
  • Behaviournative evidence
    Check is homework.Releases are a property of the machine at one moment, not of a row. One CHECK ALL with the age of the last check replaces ten buttons; native oracles run first and the network only on that press, as the runtime already does.
  • Voicethe user's side
    System-speak."launched by Puppeteer", "also installed", "update policy unknown", "identity from the native protocol", "NO IDENTITY SURFACE" describe the runtime. From the user's side these are "on PATH", "second copy", "manual", or nothing at all. A fact that cannot be known is not shown as a word in capitals.
  • Rule 2quiet default
    The default account shouts.Eight providers show Default · native root · NOT VERIFIED and four buttons before anything has happened. The common case is one account that works. Verify quietly when the drawer opens, show the identity, and let the managed accounts carry the detail.
  • §04one control recipe
    Four verbs per account.TERMINAL is the verb; verify, set default and remove are rare. One primary control and an overflow, with the default expressed by the ◆ itself, which is also the toggle.
  • Behaviourshow the state
    Signing in is blind, and the name field looks like a login.ADD ACCOUNT asks for a name, creates a root and opens a login tab elsewhere; the drawer does not say what just happened, and a text field next to "sign in" reads as if typing an address signs you in. Nothing signs in by typing: the agent's own login runs in a terminal, and the address on the row is read back afterwards. The design has to say so.
  • §05 · §07accounts elsewhere
    Accounts stop at the drawer.The usage column draws one tile per account with the provider's mark, so two Claude accounts become two identical tiles. The empty pane launches into the default account with no way to choose. The list row and the bubble name carry the folder and never the account.
  • Geometryone material
    Small drift.7px radius where the bar uses 5 and the popup 6; a shadow of its own; a fixed overlay where the inspector also lives. Take the popup's material (panel at 96%, 14px blur, 6px radius) and decide the drawer's place once.

03

The model: a profile holds one account per agent

Three words, used the same way everywhere on this page and, after this pass, in the app.

Profile

Who you are right now: Personal, Work. A named set with room for one account per agent. New terminals open into the current profile; any pane can be opened into another.

  • The first profile is made for you from what is already signed in on this Mac.
  • A new profile starts signed out everywhere; each agent signs in once.

Account

One agent's login inside a profile: Claude · me@jamesyong42.com · MAX. It lives in its own data root, so sessions, plugins and settings stay with the profile.

  • Switching the account keeps the root and changes who is signed in.
  • An agent a profile has not set up simply reads "not set up".

Signing in

Always the agent's own login, run in a terminal tab bound to the profile: Claude's browser login, Codex's ChatGPT login, Kimi's device code. Puppeteer never sees a password or a token.

  • The address and plan on a row are read back from the agent afterwards.
  • Typing a name never signs anything in.
What this changes underneathThe runtime already keeps one root per agent and binds a set of them, at most one per agent, to a terminal. A profile is that set with a name. The registry gains the named sets; the per-agent roots stay as they are; the bar's "current profile" is the defaults map that exists today. Nothing about launch, resume or usage changes.

Each SIGN IN opens that agent's own login in a terminal tab bound to the new root; the sheet watches the tab and fills the row when the identity reads back. Skip is always allowed; a half-set-up profile is a normal profile. On a Mac that already has logins, first run is one sentence on the Personal card and no wizard.

08

Switching an account, and how signing in really works

SWITCH on a row signs that agent out inside the profile and opens its login again, in a terminal tab bound to the same root. The profile's sessions, plugins and settings stay; only who is signed in changes. Anyone who wants both accounts side by side makes a second profile instead, which is what NEW PROFILE is for. The row says this before it does it.

Does typing an address sign in?No, and no design on this page has a field that does. The only text field is the profile's name. Signing in is always the agent's own flow, run in a terminal pane bound to the profile's root: Claude opens a browser and waits for its code, Codex opens ChatGPT, Kimi prints a device code, OpenCode asks for a provider in the terminal. When that pane exits, Puppeteer asks the agent who is signed in (Claude's auth status --json, Codex's account/read) and writes the answer on the row. That is where the address comes from. No password, token or address is ever typed into Puppeteer, and none is stored by it.
