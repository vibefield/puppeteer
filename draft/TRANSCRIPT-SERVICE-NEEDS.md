## What the current dependency actually is

Puppeteer's core, runtime and runtime adapters currently have **no Rosetta/Spaghetti SDK or service dependency**. RFC 003 removed that live-runtime dependency. Godview has its own Rosetta HTTP history client. Several adapters independently read provider-native files, and other adapters recover durable state through native APIs. These are different dependencies even when both contain conversation data.

| Boundary today            | Owner and consumer                                                               | What crosses it                                                                                                                              |
| ------------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Native observation        | Adapter → Core events and monitor evidence → runtime → Godview/Vibefield monitor | Conversation, turn/tool/interaction state, usage and other supported live observations. Some providers use journals as their primary source. |
| Indexed history           | Godview main-process history client → Find sheet                                 | Session titles/summaries, scoped text matches, root attribution and index availability.                                                      |
| Indexed activity          | Vibefield `IndexService` → session recovery policy                               | Recorded activity timestamps used by automatic resume-when-idle. This can lead to terminating and replacing a PTY.                           |
| Source management         | Puppeteer profiles → Vibefield enrollment/index service                          | Provider-native observation root, profile identity and its mapping to a Rosetta runtime.                                                     |
| Rosetta process/transport | Standalone Godview connection logic or Vibefield supervisor                      | Origin selection, protocol compatibility, daemon generations, database/enrollment and lifecycle. These are app implementation concerns.      |

The useful abstraction is therefore consumer-driven. An app-provided history service must not silently become a prerequisite for starting or controlling every agent. Moving live native observers behind an app-provided service would be a separate, explicit change to RFC 003, with additional delivery and correctness requirements.

### What Godview actually asks Rosetta for

The implemented HTTP surface is `/api/status`, `/api/sessions` filtered by native IDs, `/api/search`, and individual `/api/sessions/:id` reads for root attribution. There is no current Godview request for a transcript timeline, message body, history usage total, attachment, analytics query or Rosetta artifact file.

Protocol 18+ supplies native-ID filtering, session-scoped search and prefix search. The protocol-17 fallback scans recent sessions and narrows search by time before filtering locally. The client accepts versions 17–20. Supporting that legacy path is an implementation compatibility decision, not a shared product need.

The client currently caps live scope at 256 IDs and query length at 512 characters, batches native lookups in groups of 64, defaults search to 300 hits, and bounds delegated-session lookups at 32. Requests time out after eight seconds. Facts cache for 15 seconds, misses for three seconds, and version checks for 60 seconds; Find refreshes while open and debounces typing. Preserve bounded, cancellable work and explicit partial answers in a future contract; these exact tuning constants do not need to become public API.

`HistorySessionFacts` also exposes `cwd`, `updatedAt` and `streamState`, but Find's presentation/scoring currently reads title and summary. It obtains live recency from the monitor. `HistorySearchHit` exposes canonical/root IDs and title as well; the rendered hit needs its stable ID, kind, time, snippet and live-run join. Keep identifiers needed internally for resolution, but do not copy unused transport fields into a new public shape without a consumer.

`FindHistoryBridge` is already injectable through a component prop, but its types are extracted from the Electron `PuppeteerBridge`. That is a useful extraction point, not yet an independent shared service contract. Vibefield's current `index.*` RPCs cover status/discovery/enrollment/retirement; they do not yet provide Godview's Find queries.

### H06: recorded activity is not current runtime idleness

Rosetta's [SessionActivity](../../rosetta/clients/ts/generated/SessionActivity.ts) is the first/last timestamp of recorded canonical messages and native tool lifecycle events, including descendants. Its [SessionRow](../../rosetta/clients/ts/generated/SessionRow.ts) explicitly separates `updated_at` as source/metadata freshness. Neither a metadata mtime nor an ingestion tick is conversation activity.

Vibefield's `idleVerdict()` correctly refuses missing activity, non-finite/future timestamps and index failures. The index service also rejects contradictory activity bounds. However, the verdict only compares the last recorded timestamp with the threshold; it does not consult the returned `streamState`, per-session catch-up coverage, an open turn/tool, or a live idle observation. `pollPending()` can then call `replacePending(..., "idle")`, which terminates the old PTY, waits for it to be gone, and resumes the stored continuation. Existing ownership/replacement safeguards remain separate from this evidence question.

**Design risk inferred from this code:** a long model request, a blocked interaction, or delayed/incomplete indexing can produce old recorded activity while work is still in progress. Index freshness alone would not resolve the long-running-request case. Decide whether this automatic policy should remain, require additional live evidence, or give way to explicit recovery. Do not encode the current timestamp heuristic as service-level truth.

### Claude Code

[Transcript provider](../packages/adapter-claude/src/observation/transcript/provider.ts), [assistant projection](../packages/adapter-claude/src/observation/transcript/conversation.ts), [driver](../packages/adapter-claude/src/driver.ts), [resume discovery](../packages/adapter-claude/src/launch/prepare.ts).

Only root assistant content is parsed for publication. Identity/parent links and user records help order and correlate those assistant changes. Existing messages form a silent baseline on attachment; later changes publish with deduplication. Hooks trigger polls and a fallback timer polls by default. Reattachment arms this same reader before the first returning hook. Resume and recovery after an unheard `/clear` also locate/check a transcript under the selected config root; those checks do not parse content.

Native `MessageDisplay` and `Stop.last_assistant_message` overlap with assistant text. The runtime's `isCanonicalApplicationEvent()` suppresses non-replay `native-transcript` assistant events from application publication and monitor projection when observation is `native-hooks` or `structured`; they can still update agent state. In `native-log` observation they remain application-visible. Removing the reader therefore requires deciding what text/state coverage is acceptable during reattachment and degraded observation, not just proving that normal hooks emit text.

Completed removals remain excluded: settled usage/burn, historical conversation replay, model extraction/child scans, workflow journals and unknown transcript metadata. The adapter-local `SemanticObservationProvider` already offers an injection seam, but accepts a physical `transcriptPath` and includes capability/batch hooks in the default implementation. It should not automatically become the cross-provider history interface.

### Codex

[Native-TUI observer](../packages/adapter-codex/src/observation/observer.ts), [rollout context reader](../packages/adapter-codex/src/observation/rollout-context.ts), [context normalization](../packages/adapter-codex/src/normalization/context-window.ts), [TUI wiring](../packages/adapter-codex/src/launch/tui-session.ts).

Attachment calls `thread/resume`, enriches with `thread/read(includeTurns: true)` where available, and replays completed turns/items after subscribers attach. Buffered live events remain behind the replay barrier and already-replayed completed turns are deduplicated. This is native API history, not Rosetta output.

Separately, `readLastCodexContextWindow()` reads at most the last 1 MiB of `thread.path`, reverse-scanning for `event_msg/token_count`. It extracts `last_token_usage.total_tokens` and `model_context_window` to bootstrap context pressure. It is not a burn-rate or settled-request usage import. Later `thread/tokenUsage/updated` notifications supply context and compaction/model changes invalidate it. This reader is optional enrichment: failure returns no value. Decide whether unknown context until native evidence arrives is acceptable, or whether the app-server has a proven equivalent initial snapshot. The generic structured driver exposes the path but does not call this reader.

### Grok

[Discovery](../packages/adapter-grok/src/observation/session-discovery.ts), [observer](../packages/adapter-grok/src/observation/session-observer.ts), [normalization](../packages/adapter-grok/src/normalization/pipeline.ts), [monitor](../packages/adapter-grok/src/normalization/monitor.ts), [usage](../packages/adapter-grok/src/normalization/usage.ts), [control session](../packages/adapter-grok/src/services/control-session.ts).

The append-only `updates.jsonl` stream carries native ACP-shaped updates plus Grok extensions: user/assistant/reasoning text, prompt and turn correlation/completion, tools and delegated activity. The monitor also consumes durable usage, distinguishing response contributions from a turn-total remainder and ignoring incomplete usage. `signals.json` provides context/compaction/model facts; `summary.json` provides cwd/current model and helps locate moved session data; `models_cache.json` supplies context capacity. Discovery selects the latest session using file metadata.

ACP is a control/approval side channel. With the journal observer present, the binding deliberately filters overlapping ACP conversation/lifecycle events, while retaining permitted permission/context/environment and Grok extension evidence. Its existence is not proof that it observes every interaction made in the native TUI. Removing the journal requires native-TUI coverage verification, not simply redirecting the same field names. Bootstrap must also avoid treating a previous attachment's `session_end` as the end of the new binding.

### Kimi

[Session store](../packages/adapter-kimi/src/observation/session-store.ts), [observer](../packages/adapter-kimi/src/observation/session-observer.ts), [prompt service](../packages/adapter-kimi/src/services/prompt.ts), [normalization](../packages/adapter-kimi/src/normalization/pipeline.ts), [monitor](../packages/adapter-kimi/src/normalization/monitor.ts).

The session index maps IDs to session directories/workdirs, including tombstones; discovery validates paths and falls back to the cwd bucket. `state.json` supplies initial identity/environment metadata. Main and discovered child wire journals carry turn prompts/steps/endings, assistant and reasoning parts, tools/results, interactions, model/configuration and context changes.

Prompt submission registers an expectation before terminal injection and confirms against a matching **live** durable `turn.prompt`; discovery may use that match to bind a newly created session. Replay must not confirm a new submission. The portable event normalizer primarily handles the main agent, but the separate monitor path consumes child records too: child status/delegation, observed `llm.request` model/effort, `usage.record` token buckets/context, questions and resolution, permission/session modes, and compaction/context invalidations. Child journals are therefore not an unused metadata lane. Swarm/goal/cron-like records that do not prove a stable portable fact remain raw.

### Copilot

[Store](../packages/adapter-copilot/src/observation/session-store.ts), [observer](../packages/adapter-copilot/src/observation/session-observer.ts), [prompt service](../packages/adapter-copilot/src/services/prompt.ts), [normalization](../packages/adapter-copilot/src/normalization/pipeline.ts).

The known session UUID locates `events.jsonl`; resume validates access and captures the replay boundary. `user.message` confirms injected prompts. Records supply session/environment/model/effort/mode, turns, assistant/reasoning, tool requests/execution, permissions, compaction, delegation and file changes. Assistant usage and shutdown summaries also contribute usage evidence. Actor and interaction IDs distinguish child work and tool continuations from terminal turn completion. Deleting the journal loses these features; reducing old replay or duplicate usage summaries needs a narrower, separate audit.

### Pi

[Store](../packages/adapter-pi/src/observation/session-store.ts), [observer](../packages/adapter-pi/src/observation/session-observer.ts), [prompt service](../packages/adapter-pi/src/services/prompt.ts), [normalization](../packages/adapter-pi/src/normalization/pipeline.ts).

Discovery reads bounded session headers for native ID/cwd and supports exact or unambiguous prefix resume. The journal supplies user/assistant messages, tool calls/results and workspace effects, turn outcomes, model/effort changes, compaction/context invalidation, message usage and summary usage. It is the currently wired native-TUI semantic source. The provider can persist a user prompt only when the first assistant record is flushed, so Pi deliberately does **not** promise durable prompt acceptance from its prompt API. A shared history abstraction must not upgrade that uncertainty.

### Antigravity

[Store](../packages/adapter-antigravity/src/observation/session-store.ts), [observer](../packages/adapter-antigravity/src/observation/session-observer.ts), [prompt service](../packages/adapter-antigravity/src/services/prompt.ts), [normalization](../packages/adapter-antigravity/src/normalization/pipeline.ts).

Fresh-session discovery compares candidate IDs with the launch baseline and scans bounded content for the submitted prompt. Peer claims and ambiguity handling prevent assigning the same conversation to concurrent launches. `USER_INPUT` confirms the prompt; `PLANNER_RESPONSE`, tool-result types and `ERROR_MESSAGE` drive derived reasoning/conversation/tool/workspace/turn events. Step indices and expected result types are needed to correlate them. `CHECKPOINT` alone does not prove compaction. This journal does not establish supported token usage or observed model/context coverage; do not add those to the shared requirements on the strength of a field name.

### OpenCode, Hermes and ACP

OpenCode [driver reconciliation](../packages/adapter-opencode/src/driver.ts) and [history projection](../packages/adapter-opencode/src/observation/history.ts) query the root and children, messages, current statuses, pending permissions and pending questions. Bootstrap and SSE reconnection use those snapshots to close gaps and replace stale evidence, retaining replay/resync provenance. These are not all optional old chat rows: deleting reconciliation can lose current blockers, child state and request correlation. Historical display replay can be assessed separately from current-state recovery.

Hermes [driver](../packages/adapter-hermes/src/driver.ts) distinguishes the stored conversation ID from the gateway's live ID. On resume it publishes returned assistant messages as bootstrap/replay and then drains buffered gateway events. This assistant display replay is removable independently of the native `session.resume` operation; the latter binds/control-resumes the session.

ACP [driver](../packages/adapter-acp/src/driver.ts) loads through `session/load`, receives replayed notifications, seals replayed assistant output and applies returned configuration. Resume support and native request/response ownership belong to the adapter. An index lookup cannot substitute for the protocol's load/control operation.

[Core monitor types](../packages/core/src/monitor/types.ts), [runtime ingress](../packages/runtime/src/runtime.ts) and [monitor service](../packages/runtime/src/services/monitor-service.ts) are existing contracts to preserve, not duplicate in an index schema.

The [shared JSONL tail](../packages/native-observation/src/jsonl-tail.ts), used by Copilot/Pi/Antigravity, distinguishes replay by a captured byte boundary, tracks source generations, diagnoses replacement/truncation, retains partial records and bounds work. Defaults are 64 KiB reads, 4 MiB per poll, 1 MiB per record and 16 MiB replay. Grok and Kimi have dedicated bounded readers; Claude has its bounded, yielding snapshot/delta reader. Journal observers commonly poll at 75–100 ms; Claude's fallback is slower and supplemented by hooks. Any outsourced live service needs an explicit delivery budget and overload behavior, not a promise that eventual indexing is equivalent.

Rosetta already has a [snapshot/change subscription client](../../rosetta/clients/ts/client.ts), including session timeline snapshots, mutations and reset/resync handling. It is **not limited to search**. However, neither Godview nor these adapters currently use those subscriptions, and this audit has not established equivalence for prompt gates, native actor/turn identities, corrections, source coverage or latency across providers. A live-service migration needs that mapping and validation before selecting Rosetta as the implementation.

## Completed API cleanup

The user requested complete removal of the runtime's `agent.conversation` timeline after reviewing this inventory. Removed the getter, `AgentConversationService`, its snapshot/item types, unconditional per-Agent projection and the deprecated `runtime.conversationSnapshot()` alias. There is no replacement runtime timeline or history buffer.

Normalized `conversation:assistant-message` events still serve typed subscribers and the independent state/monitor projections, including Godview's bounded last-response display. The Godview spawn smoke check now observes prompt, final reply and completion events directly. ## Constraints for the later interface design

1. **Scope identity explicitly.** Core already has a namespace-bearing `NativeSessionRef`; current history joins discard that namespace and use the ID alone. Provider namespace alone is also insufficient when profiles/roots or hosts contain copied sessions. The app needs an opaque source/index scope, plus native identity, and must handle ambiguous/unindexed results. App/user authority may be bound to the service instance rather than repeated in every argument. Physical roots, Rosetta kind (`claude-code`) and Puppeteer provider (`claude`) are app-adapter mapping concerns.
2. **Do not conflate identities or operations.** Native conversation, canonical index row, root conversation, live gateway session, Puppeteer run and runtime epoch have different lifetimes. `/clear` can rotate native identity. An index fact does not prove the native session can be resumed or that a process still exists.
3. **Make scope narrowing monotonic.** Godview's current empty native-ID scope means global search; Find filters returned hits back to live rows. A proposed shared live-Find query should define empty scope as empty, and require an explicit different operation/capability for global search. Unsupported filters, limits or missing roots must not silently widen a query.
4. **Separate answer state from data.** Unavailable, unsupported, ambiguous, not indexed yet, authoritative absence, partial and stale are not interchangeable empty arrays. Canonical readiness means queries can be served, not that every source/session has been ingested. Search readiness is independent. Keep prior answers only with clear freshness, and bound caches by source/generation and query scope.
5. **Keep history time distinct from observation time.** Recorded event time, metadata update time, query time, ingest progress and current live state answer different questions. Usage replay must not count as new live work. H06 cannot infer negative live evidence solely from a quiet historical timeline.
6. **Keep implementation ownership visible.** Standalone Godview supplies its external-daemon client; Vibefield supplies an implementation using its owned daemon and transport/authentication. The common interface should not expose a URL or let a consumer choose a different daemon behind the app's back. Protocol negotiation, origin changes, timeout/retry and schema decoding remain implementation responsibilities.
7. **Reuse the right existing boundary.** Extracting a consumer-owned query contract from Find is smaller than injecting Rosetta into runtime. If runtime later needs indexed facts, inject only that interface/capability. If adapters later delegate live durable observation, use a separately specified source contract feeding existing events/monitor evidence. Do not grow `AgentHost` into a database client or expose arbitrary paths/raw record streams as a shortcut.
